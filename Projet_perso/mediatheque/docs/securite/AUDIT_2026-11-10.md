# Audit de sécurité : fin du palier P1 (10/11/2026)

Périmètre : `src/mediatheque/` après P1 (`stockage_sqlite.py`, `reservation.py` et les réservations dans `mediatheque.py`, `auth.py`, `session.py`, `init_db.py`). Il n'y a pas encore d'interface graphique.
Modèle de menace retenu : l'interface Tkinter (P2) ne doit appeler que `Session`, et le contrôle des rôles doit tenir **dans la couche métier**, même si l'interface comporte un bug. Un attaquant peut aussi avoir un accès en écriture au fichier `.db`, par exemple sur un poste partagé.

## Résumé

| Gravité | Nombre |
|---|---|
| Critique | 0 |
| Haute | 0 |
| Moyenne | 3 (S1, S2, S3) |
| Basse | 4 (S4, S5, S6, S7) |

Les bases sont saines : scrypt avec sel, `compare_digest`, messages d'erreur uniformes, SQL 100 % paramétré, sauvegarde transactionnelle, rôles contrôlés dans `Session`. Les failles viennent surtout de ce que **`Session` laisse entrer** (une date choisie par l'appelant) et de ce qu'**elle laisse sortir** (des objets métier modifiables), ainsi que d'un contrôle d'intégrité incomplet au chargement.

## Points vérifiés et sains

- **Hachage** : scrypt, sel de 16 octets issu de `secrets` et propre à chaque compte, jamais de mot de passe en clair. `Compte.__repr__` masque le hash (`auth.py:29-30`, `auth.py:54-55`, `auth.py:86`).
- **Comparaison en temps constant** : `hmac.compare_digest` (`auth.py:108`).
- **Énumération de comptes** : message identique pour un identifiant inconnu ou un mauvais mot de passe. Le hachage est calculé aussi pour un identifiant inconnu, avec un sel leurre (`auth.py:105-107`), et le blocage se comporte pareil dans les deux cas. La seule fuite est `creer_compte` (« identifiant déjà utilisé »), réservé au responsable, donc acceptable.
- **Blocage non contournable** par la casse ou les espaces : l'identifiant est normalisé par `strip().lower()` à la création et à la connexion (`auth.py:81`, `auth.py:99`). Pendant le blocage, même le bon mot de passe est refusé. `changer_mot_de_passe` passe par `authentifier` et ne peut donc pas servir à une attaque par force brute.
- **Contrôle d'accès** : toutes les méthodes responsable portent `@responsable_requis`. Un adhérent ne peut pas cibler un autre numéro, y compris avec les variantes `"A001 "`, `"a001"` ou `""` (`session.py:60-69`). Le responsable ne peut pas cibler un numéro inexistant. Une session fermée est refusée.
- **Injection SQL** : toutes les requêtes utilisent `?`, et `SCHEMA` est une constante. Une charge `x'); DROP TABLE documents; --` fait l'aller-retour sans effet.
- **Base falsifiée** : rôle inconnu refusé même si la base a été fabriquée sans `CHECK` (`auth.py:48-52`). Un compte adhérent sans numéro, lié à un adhérent inexistant, ou un second compte pour le même adhérent est refusé (`mediatheque.py:48-54`). Les emprunts et réservations orphelins sont refusés.
- **Sauvegarde transactionnelle** : un échec (par exemple une violation de clé étrangère) laisse la base dans son état précédent (`stockage_sqlite.py:91`).
- **Écrasement de fichiers** : `mediatheque-init` refuse un fichier existant (`init_db.py:19`) et demande le mot de passe par `getpass`, jamais en argument.
- **Fonctions dangereuses** : aucun `eval`, `exec`, `pickle`, `subprocess`, `os.system` ni `yaml` dans `src/`.
- **Secrets** : aucun `.db` ni mot de passe dans l'historique git (`git log -p`). `*.db` est dans `.gitignore`. `data/` ne contient que des noms fictifs.
- **Dépendances** : aucune dépendance d'exécution. Dépendances de développement : pytest 9.2.0, pluggy 1.7.0, pygments 2.21.0, packaging 26.3, iniconfig 2.3.1, colorama 0.4.6. `pip-audit` n'est pas installé, donc l'absence de CVE est **à confirmer**.

## Points à surveiller en P2 (non comptés comme failles)

- `export_retards_csv(chemin)` et `Mediatheque.sauvegarder(destination)` écrivent et écrasent sans confirmation à n'importe quel chemin (`rapports.py:40`, `mediatheque.py:110-128`). Ils ne sont pas exposés par `Session` aujourd'hui. Quand l'interface les exposera, passer par `filedialog.asksaveasfilename` (qui demande confirmation) et ne jamais construire le chemin à partir d'une saisie libre.
- La sauvegarde CSV (`stockage.py`, `ecrire_*`) n'est pas atomique (écriture directe avec `open("w")`). Ce n'est plus le format principal, mais il vaut mieux écrire dans un fichier temporaire puis faire `os.replace` si on le garde.
- Le fichier `.db` contient les hashes : il faut le placer dans un dossier dont les droits sont réservés à l'utilisateur de l'application.
